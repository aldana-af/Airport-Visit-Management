The real fix — make LoginID nullable, not populated. A NULL foreign key value is always valid in SQL Server regardless of what's in the parent table — the FK constraint only checks non-null values. So instead of inventing fake Logins rows, we just stop requiring a value at all:

sql
ALTER TABLE EmployeeHost ALTER COLUMN LoginID INT NULL;
ALTER TABLE SiteVisitingManager ALTER COLUMN ManagerLoginID INT NULL;

Then, matching the pattern we used for Name/Email/Role earlier — mark the C# properties nullable too:

EmployeeHost.cs:

csharp
public int? LoginID { get; set; } // Foreign key to Logins table

SiteVisitingManager.cs:

csharp
public int? ManagerLoginID { get; set; } // Foreign key to Logins table

No AdminController.cs changes needed — since you never set LoginID there, EF will now correctly send NULL instead of defaulting to 0, and the insert will go through cleanly.
